## Expected Dataset Shape

Current working assumption: one row represents one component status observation for one machine.
This lets each machine have dynamic component counts and arbitrary tooltip metadata.

Open decision: confirm whether source data is component-level rows, machine-level snapshots, or a
hybrid.

## Data Roles

| Role | Kind | Required | Description | Constraints |
| --- | --- | --- | --- | --- |
| machineId | Grouping | Yes | Stable unique machine key. | Must uniquely identify a machine across updates. |
| machineName | Grouping | No | Display label for the machine card. | Falls back to `machineId` if absent. |
| machineType | Grouping | No | Machine category, such as digger or excavator. | Optional display/filter metadata. |
| componentId | Grouping | Yes | Stable unique component key/tag. | Must be unique within machine; global uniqueness preferred. |
| componentName | Grouping | No | Human-readable component name. | Falls back to component category/order/tag. |
| componentCategory | Grouping | Yes | Component category. | Expected values: tooth, lip shroud, wing shroud. Exact enum TBD. |
| componentOrder | GroupingOrMeasure | Conditionally | Physical/order index for teeth, lip shrouds, and wing shrouds. | Needed for deterministic ordering. |
| componentSide | Grouping | Conditionally | Side for wing shrouds. | Left/right or derived from odd/even rule. |
| status | Grouping | Yes | Current component status. | Status mapping TBD: exact strings vs configurable aliases. |
| lastSeen | Grouping | No | Last timestamp/data update for component. | Timezone/format TBD. |
| tooltipFields | GroupingOrMeasure | No | Additional report-author-selected tooltip fields. | May accept multiple fields. |

## Data View Mapping

Chosen mapping: likely `categorical` with grouped categories, or `table` if flexible tooltip fields
and component-level rows are easier to support.

Rationale:

- The visual needs one logical record per machine component.
- Machine/component/category/order/status fields must be read together.
- Optional tooltip fields may vary by report.

Decision needed before implementation: choose `categorical` vs `table` after confirming row shape and
Power BI field well UX.

Expected shape:

- Machine grouping.
- Component grouping.
- Component category and order fields.
- Status field.
- Last seen and optional metadata fields.

## Data Limits

- Maximum machines: 20.
- Teeth per machine: 4 to 20.
- Lip shrouds per machine: inferred as `teeth - 1` or supplied rows - TBD.
- Wing shrouds per machine: 0 to 8 total, up to 4 per side.
- Maximum GET component records: roughly 20 machines * (20 teeth + 19 lip shrouds + 8 wing shrouds) =
  940 component rows before tooltip metadata.
- Reduction strategy: TBD. Likely reject/guide above supported limits rather than silently truncate.
- Aggregation/paging strategy: TBD. Visual likely needs all relevant current component rows at once.
- Geometry strategy: bucket body, cutting edge, side plates, teeth, lip shrouds, and wing shrouds
  should be derived from component counts and available card size.
